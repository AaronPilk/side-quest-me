# Sidequest database

Postgres is the sole relational authority. Apply `supabase/migrations/*` and then `supabase/seed.sql` to a **new, explicitly selected Sidequest project**. The seed contains thirty authored quest variants, no sponsors, funded offers, balances, or operator accounts. A fixture is not funding.

`node scripts/db-test.mjs` creates an isolated, temporary PostgreSQL cluster with a private Unix socket, installs minimal Auth test tables/roles, rebuilds migrations and seed, runs actual transactions/concurrent sessions/RLS checks, and shuts down/removes that cluster. Requires `initdb`, `pg_ctl`, and `psql` (`pg_config --bindir` is supported). It never connects to a live project. `node scripts/db-test.mjs --advisors` also runs the Supabase CLI security advisors using an ephemeral loopback TLS listener/certificate, then removes them. Observed on PostgreSQL 17 / CLI 2.101.0: no security issues at warning/error level. These tests prove database behavior, not live Supabase Auth delivery or hosted Data API configuration. The Auth fixtures model the columns used by the app; they are not deployed migrations. `node scripts/db-test.mjs --generate-types` generates `shared/database.generated.ts` from actual migrated table columns, foreign keys, and RPC signatures; it uses local SQL introspection so Docker and hosted credentials are unnecessary. `shared/database.types.ts` is a separately labeled narrow hand-authored DTO layer.

## Provision the explicitly selected staging project

`supabase/config.toml` is a reduced CLI-generated local configuration (CLI 2.101.0): project label `sidequest`, Postgres 17, only `public` exposed, migrations enabled, and `./seed.sql` selected. `private` remains unexposed. R2 is the only application media store. The local project label is not a hosted account/project reference. Match `db.major_version` to the chosen project's actual PostgreSQL major version before local/remote schema comparison.

From the repository root, set `SIDEQUEST_PROJECT_REF` yourself to the verified **fresh Sidequest staging** project reference, then run the following commands. They are deployment instructions; no link or push was performed during this build. Authenticate with `supabase login` first if the CLI is not already authenticated. Let the CLI prompt for the database password or use your approved secret mechanism; do not commit it.

```sh
: "${SIDEQUEST_PROJECT_REF:?Set this to your verified Sidequest staging project reference}"
supabase link --project-ref "$SIDEQUEST_PROJECT_REF"
supabase db push --linked --dry-run --include-seed
# Review the listed migration and authored quest seed before applying.
supabase db push --linked --include-seed
supabase migration list --linked
supabase db advisors --linked --type security --level warn --fail-on warn
```

`--include-seed` loads only the thirty authored variants; it creates no sponsor, campaign, redeemable reward, wallet credit, or operator. Keep staging and production project links/credentials separate. A future production push needs its own explicitly checked target and migration review.

The committed Auth callback URLs are local development URLs. Configure the chosen hosted project's Site URL and exact deployed `/auth/callback` URL in Auth settings, plus its email delivery settings. Do not push this local Auth configuration blindly to production with `supabase config push`.

Parser validation used the installed CLI's read-only `supabase status`: the valid file reached the local container-status check, which stopped because Docker is unavailable. A temporary invalid integer produced `failed to parse config`, confirming that the same CLI parser read and validated the file. No local Supabase stack or hosted project was started or modified. Actual schema/security tests use the isolated PostgreSQL runner described above.

## Trust boundary and SQL API

Every `sq_*` RPC is `SECURITY INVOKER`, has an empty controlled search path, and revokes execution from `PUBLIC`, `anon`, and `authenticated` for its exact signature. Only the server `service_role` may execute it. The Worker must derive `p_actor` from a verified nonanonymous Auth user and live session, never from a request body. It must validate strict request schemas and recommendation constraints before calling. RLS remains enabled on every application table, with explicit browser grants and ownership policies. Browser profile writes have a column allowlist; no browser can alter account status, snapshots, balances, roles, token material, or ledger.

All actor mutation RPCs below take `(p_actor uuid, p_input jsonb, p_key text, p_hash text)` and return JSON. The Worker hashes the canonical validated request and retains the key through transport retries. Keys are actor/operation scoped, 8–128 characters. Same key/different hash raises `idempotency_conflict`. Idempotency rows commit with the mutation. Permanent unique run/asset ledger events prevent additional awards with fresh keys. Error messages are short domain codes; the Worker maps them to its sanitized error envelope.

`clips` is exactly three distinct sealed source slots, each `{asset_id,start_ms,end_ms,mute?,fit?,crop?,label?}`. `fit` is `cover` or `contain`; `crop` is 0–1, default 0.5. Selected segments are 5–15 seconds and bounded by the trusted source duration. Source cap is 40 MiB/60 seconds, thirty-six source generations per run and 2 GiB of active/pending objects per account. Saved reels are capped at fifty. Output cap is 100 MiB. Keys are `staging/{owner}/{asset}`, `sealed/{owner}/{asset}/{random-64-hex}` and `renders/{job}/{fence}/{64-hex}.mp4`. Key names confer no authorization: all R2 objects remain private. The sealed nonce need not equal content SHA; trusted validation records actual SHA separately.

Other service-only RPC signatures:

- `sq_upsert_profile(p_actor uuid,p_input jsonb)` initializes profile/wallet for an existing Auth user and edits only `display_name,timezone,locale,preferences,imported_summary,onboarding_complete`. Roles do not come from preferences or Auth user metadata.
- `sq_finalize_account_deletion(p_actor uuid)` runs only for an already deleting/deleted account, after all object cleanup succeeds. It redacts run/renderer content, outing fields and captions, removes private token and idempotency response material, preserves audit hashes and committed financial facts, and returns `ready_to_delete_auth:true`. This is the single narrowly checked deletion exception to accepted/evidence immutability. Call it before Auth Admin deletion and final profile status `deleted`.
- `sq_check_session(p_actor uuid,p_session uuid)` requires a live `auth.sessions` row, a nonanonymous `auth.users` record, and no disabled/deleting profile. Recheck on sensitive operations. Profile status immediately blocks old JWTs after deletion.
- `sq_eligibility(p_actor uuid,p_family text)` returns `{eligible,reason,reset_at}`. Eligibility is advisory until finalization.
- `sq_review_evidence(p_actor uuid,p_run uuid)` returns the immutable manifest/snapshot for a current operator reviewing someone else's pending run and records an access audit event.
- `sq_schedule_retention(p_limit int default 100)` atomically marks expired pending uploads and eligible thirty-day sources deleted and queues cleanup, with profile/run/asset locks. It preserves pending/review/failed export evidence and final reels.
- `sq_memberships(p_actor uuid)` returns the current actor's active operator/merchant scopes.
- `sq_operator_state(p_actor uuid)` returns templates, reviews, offers, sponsors, campaigns, recent redemption states and failed render jobs; requires current operator membership.
- `sq_redemption_material(p_actor uuid,p_redemption uuid,p_token_hash text default null)` returns an owned unexpired reservation with persisted nonce/key version. Worker signs deterministic claims using a maintained cryptographic library; call again with its SHA-256 to bind the resulting token. A differing second token hash fails. No plaintext token is persisted. The consumption transaction checks hash/scope/state after Worker signature/expiry verification.
- `sq_claim_render(p_job uuid)` claims one eligible job, increments `fence`, and leases it for ten minutes, or returns null for duplicate/terminal/currently leased work. Maximum three automatic attempts. Explicit owner retry of a failed transient job uses `sq_request_render`: sixty-second cooldown, at most three manual retry cycles, fresh fencing token, and outbox reset. Nontransient failures require changed inputs. None of these paths write reward ledger entries.
- `sq_finish_render(p_job uuid,p_fence bigint,p_output jsonb)` promotes only an unexpired current lease; output contains `object_key,bytes,mime,duration_ms,sha256,metadata`. Metadata can include `thumbnail_key`. Deleted accounts/sources cannot promote output.
- `sq_fail_render(p_job uuid,p_fence bigint,p_error text)` retries only `network`, `capacity`, `interrupted`, up to three attempts. Stale attempts do not change a newer lease.
- `sq_reconcile(p_limit int default 100)` expires reservations/refunds once, closes fourteen-day reviews with zero award, and re-arms undispatched/expired jobs. Call from the existing scheduled recovery pass.
- `sq_wallet_audit(p_actor uuid)` compares all wallet projections with immutable ledger sums and records an audit event. It reports mismatches; it never silently rewrites history.

## Locks, invariants, and retention

Normal mutations check/hold the active profile, then their idempotency record. Economy operations lock wallet, owned run/redemption, then shared offer; multiple assets lock in ascending UUID order. The wallet lock serializes the actual award boundary: at most three rewarded completions per UTC calendar day, and thirty elapsed days between awards to the same family across levels. Server time and the immutable accepted award policy determine amounts. Review-needed freezes evidence before releasing the active-run slot and earns nothing until approved. Editing/rerendering never changes the submitted manifest or awards. Completion inserts the render job and outbox in the same transaction. Dispatch after commit may repeat; fenced leases make repetition safe.

Reward reservation atomically rechecks offer version/window/funding/approved merchant/area/stock/per-user limit/balance, snapshots price and terms, debits once and reserves one unit. Consumption, cancellation, and expiry use the same wallet/redemption/offer order. Only a reserved token can transition; consumed tokens cannot be refunded. Refunds use the snapshotted debit even after price changes. Funding references are operator records, not automated proof that a business agreement exists.

Profile deletion blanks display name, preferences and imported text immediately, closes unresolved reviews with zero award, refunds outstanding reservations, revokes shares/memberships, cancels active renders, marks media inaccessible, and creates retryable `media_cleanup` rows. Worker must remove every object, thumbnail, and staging object, mark cleanup complete, invoke `sq_finalize_account_deletion`, revoke Auth sessions/delete Auth user through Admin API, then mark the profile `deleted`. Finalization removes private outing/budget/area/role/declaration/caption content and stored idempotency responses. It retains opaque family/template/run references, original content hashes, committed award decisions, redemption business terms and ledger/audit facts; a redaction timestamp explicitly distinguishes the remaining hash from the intentionally removed original content. `profiles.auth_user_id` becomes null on Auth deletion; the opaque profile primary key remains only to preserve ledger/redemption/audit referential integrity. A retained economic identity does not grant app access. Operational retention and legal justification need the pilot operator's policy; do not represent indefinite accounting retention as a universal legal requirement.

Raw sources target thirty-day retention; unresolved reviews expire after fourteen days; final reels remain private until explicit sharing/deletion, with a fifty-reel account limit in product configuration. Do not purge the only source while an export is failing. The API scheduled task is responsible for enforcing storage retention and completing queued cleanup. The database enforces cleanup access revocation and cancellation independently of object deletion. Downloaded copies cannot be recalled; serving shares must recheck revocation and use no-store/short object authorization lifetimes.

## First operator and real offers

After the intended operator signs in, use the selected project's SQL editor/admin connection (never a public endpoint):

```sql
insert into private.role_memberships(user_id,role)
select id,'operator' from public.profiles
where auth_user_id = '<verified-operator-auth-user-uuid>'::uuid;
```

Use a reviewed real UUID; there is no seeded operator or role-grant route. Merchant membership similarly uses role `merchant` with the exact approved `merchant_id`. Revocation sets `revoked_at=now()` and takes effect on the next operation, independent of JWT refresh.

The operator records a real sponsor with approved identity/area and private agreement/funding reference, then publishes an offer with funded inventory, terms, dates, currency and point price. Only active, currently valid, funded, non-demo offers with an approved merchant are publicly readable. To disable an offer, call the operator update with `active:false`; honor already reserved snapshotted terms or cancel/refund deliberately. Use `sq_pause_campaign` to disable future campaign placement. Campaigns have explicit date windows, areas, approved family/category arrays, a plain-text disclosure, and a private funding reference/notes record. Active publication requires an approved sponsor and funding recorded by an operator; this record does not claim that software independently verified payment. No sponsor/campaign is seeded. Recommendations first obey every ordinary hard filter, then optionally display one matching campaign; there is no sponsored ranking boost. Acceptance rechecks active window, funding, approved sponsor, exact area, category and family, selects the earliest matching campaign by creation time/ID, and freezes its identity/version/disclosure. The Worker always supplies the reviewed `expected_campaign` identity/version (or JSON null for an unsponsored card). A changed match raises `campaign_changed` atomically before creating any run, so the user can review the current disclosure. Service-only maintenance callers that omit that key retain compatibility. That label becomes `sponsorDisclosure` in the immutable renderer manifest, so later edits or pausing never silently change an already accepted agreement. Campaigns cannot create venue permission, relax exclusions, hide costs, increase completion awards, or require sharing. Public campaign DTOs contain no funding references, contacts, or private notes. There are no prize-drawing, car, paid-entry, or consumer-checkout tables/endpoints.

Published template content is immutable. To edit it, create a new version and unpublish the superseded version. Existing runs continue to reference their accepted snapshots. Inventory changes cannot move already reserved or consumed units. Failed render recovery operates on jobs/outbox and never touches ledger records.
