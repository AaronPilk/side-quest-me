# Sidequest — verification of Codex's audit repairs (2026-10-05)

Scope: independent check of the uncommitted repair pass Codex made in response to `docs/CLAUDE_AUDIT_2026-10-04.md`, as summarized in `docs/CLAUDE_AUDIT_RESPONSE_2026-10-05.md`. ## 1. Short verdict

Codex's repairs hold up. The structural problems behind Full Send quality (F1) and the forced adult labels (F2) are fixed in the generator, the reviewer, the shared eligibility code, the client preflight and the acceptance RPC, and they agree with one another. The ten audit scenarios all pass live on the **final** prompt revision — the one Codex could not get a completed sample for because of two provider timeouts — with no timeouts in my run and no hidden-candidate leaks in any fallback text. The UI fixes (F6, F11) and the age-confirmation regression fix are verified in unit and browser tests.

One regression slipped through because the full browser suite was not rerun: the F6 rename orphaned four page-level CSS rules, which made the preferences wizard overflow the 390 × 844 viewport. I fixed the four selectors (two files Codex had not touched) and the affected specs pass again; the full suite is otherwise green (288/290 before the fix; the two failing scenarios and their sibling specs pass after it, 29/29).

What this pass does not change: the App Store conclusion from the audit stands. The remaining blockers are operational, not code: a physical-iPhone recording/draft/export session, production email delivery, a named moderation operator, App Privacy and age-rating declarations, a new iOS build carrying the rename and these fixes, and the migration + Worker deploy sequenced correctly. TestFlight Build 15 is still the old code and still says "Demon".

Two things worth the owner's attention that were not in Codex's write-up: the Full Send generator now clusters on the examples the prompt itself names (live-actor horror, an aerial ropes/zip course, a spontaneous overnight) across both Codex's and my runs, and the proposal call runs within a few seconds of its 60-second cap, so provider-side slowness will surface to users as fallbacks rather than suggestions. Details in §4.

## 4. New observations

### 4.1 The Full Send generator anchors on the prompt's own examples

`EXPERIENCE_CREATIVE_DIRECTION` now says "for example an operator-led adrenaline experience, a live-actor horror attraction, or choosing and booking a spontaneous unfamiliar destination for a whole night away" and adds "These illustrate scale, not required activities." The model treats them as the menu anyway. The fixture file has six Full Send scenarios, so twelve Full Send samples exist on the repaired prompts (Codex's calibrated run plus mine). The selected activity was live-actor horror four times, an aerial ropes/zip course four times, an overnight stay twice, and something else only in the two post-horror rerolls: indoor skydiving in Codex's run, wire flight at a stunt studio in mine (with indoor skydiving as the written fallback). The two "after a previous suggestion" cases show what this means for a real user: the first reroll moves from the bowling suggestion to the horror example, and the second reroll, with horror used up, reaches for operator-dependent adrenaline that a given city may not have ("a professional stunt studio offering beginner wire flight" within 15 transit minutes tonight is a stretch almost everywhere, including ours). The reviewer accepts it because the prompt allows "a different type of place with its operator, slot and complete price explicitly awaiting confirmation", so feasibility is asserted rather than checked.

This is a hypothesis about variety from ten samples, not a confirmed defect, and the quality gate is doing its job. The cheap test is to run the fixture file three more times and count distinct activity families per Full Send scenario; the cheap fix, if it reproduces, is to rotate or remove the concrete examples from the creative direction and let the rubric's "ordinary version vs. actual difference" test carry the definition, which is what the reviewer already relies on.

### 4.2 The proposal call is running close to its ceiling

The comparison-plus-proposal call has an 8,500-token output budget and a 60-second timeout (`worker/ai-provider.ts` also clamps to 60 s); the whole route has a 90-second deadline and the client waits 110 s. My ten cases took 42–67 s end to end for both calls, which puts the proposal call alone somewhere around 35–55 s at `reasoningEffort: "low"`. The prompt grew in this pass (the full rubric now rides along with the discovery rules, each of the three concepts carries two extra sentences, and the reviewer fills a four-field assessment), while the output targets for the discovery call are unchanged (~650 tokens of concepts plus ~1000 of proposal; the ~950 concept target applies to the authored-draft path). When the provider is slow, the user does not see an error: the route catches the generation error and serves a curated fallback, or the new "couldn't finish a reliable suggestion" 503 when no fallback is viable. That is the right behavior, but it means provider latency silently converts into fallback rate. Worth watching in production logs after deploy (count of `discovery_unavailable` and of fallback-served proposals per day) before judging the generator's real-world hit rate.

### 4.3 Residual opt-in labelling in the curated fallback

`worker/curated-experiences.ts` still derives adult labels from the opt-in for one option: `live_show` sets `conflicts: adult_venues` and `adultOnly: true` whenever `outing.adultContext` is on, regardless of what the show is. With `usesAdultVenueContext` that means an opted-in user who lands on the live-show fallback must confirm venue permission and adult eligibility for an unrestricted concert. It only triggers when generation fails and the listings include a show venue, so it is low impact, but it is the same pattern F2 removed from the generator. `spontaneous_staycation` is `adultOnly: true` unconditionally and also picks up the `adult_venues` conflict from the opt-in; the first is defensible for a hotel booking, the second is the same pattern.

### 4.4 Adult labels without adult content are still possible

The post-generation check catches "adult content without adult labels" but not the reverse: a proposal may set `supportsAdultContext`/`adultOnly`/`minimumAge` without tagging `alcohol` or `adult_venues`. The prompt tells the model not to, and none of the ten live samples did it, so this is a note rather than a finding. If it ever shows up in production proposals, the fix is a one-line mirror of the existing check.
