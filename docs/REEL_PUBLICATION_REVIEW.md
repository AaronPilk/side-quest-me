# Reel publication review

Finished reels remain private. Choosing **Submit for review** creates a pending publication, not a public post. Its owner can still access the run, original clips, finished reel and private journal. Completion, XP and rewards are separate from publication approval.

An independent account with the server-granted `operator` role reviews submissions at `/admin`. The queue includes the exact video, audio, public caption and shared quest instructions. An operator must review the whole submission, record notes and approve or return it for changes. The operator cannot approve their own video. A version check prevents an older review from approving a caption edited while the review was open. The owner receives an Activity notification and can see rejection notes on the publication page.

Approval makes only the reviewed version public. Any caption, brand inquiry opt-in or republication edit removes the prior approval and returns the post to the queue. Withdrawing a submission makes it unpublished; removal by moderation cannot be bypassed by its owner. Anonymous feed/detail/media reads, other accounts, inspiration links and brand inquiries cannot access a pending, rejected, unpublished or removed reel. Commercial media access also requires the post to remain approved and published. Suspending public availability preserves the exact licensed asset and agreement history but pauses download access.

Apply `20261002203133_reel_publication_review.sql` before deploying the new Worker. Existing published posts are moved to pending for their first explicit publication review; private originals and commercial history are preserved. This migration adds no automatic approval. Worker review previews use `/api/community/reviews/:id/media`; every video, thumbnail and range request checks the active operator account through the database. Ordinary clients cannot execute the service-only review RPC or the preserved prior mutation functions.

The queue is an operational tool, not a staffed moderation service. The owner must appoint operators, arrange timely review and report handling, and enforce published community standards. Public profile and Series text use the separate provider gate below. This change does not verify users' ages. Content rating and age controls must match the actual launch audience and content. Existing unlisted, expiring `/s/:token` share links remain separate from community publication; possession of an owner-created link can deliver that private reel without this queue's approval.

## Appointing a moderator

No operator membership has been provisioned by this work. The owner must first authorize the specific reviewer account and arrange who will handle submissions and reports. Have that reviewer create an account, verify its active `public.profiles.id` against the intended person, and use an authorized server/database administrative channel to add an unrevoked `private.role_memberships` row with `role='operator'` and `merchant_id=null`. Reuse an existing membership by clearing its revocation rather than adding a duplicate scope. Record the owner's approval and account identity in the operational record. Never grant the role from a client, public signup, or an unverified email alone.

The reviewer signs in and opens `/admin`. Test a submission from a different creator account, watch the whole video with audio, examine the caption and shared quest instructions, record review notes, and exercise return-for-changes and approval. A reviewer cannot approve their own reel. The operator also needs to check the report queue and remove content when appropriate; the code does not supply moderation staffing, working hours or a response-time guarantee. Revocation sets `revoked_at`, and subsequent preview/approval requests fail their role check.

Validated locally with isolated PostgreSQL invariants and Supabase security advisors, TypeScript/unit checks, and browser flows covering submission, rejection, resubmission, approval, editing, withdrawal, ownership and Series publication. No migration or deployment is performed by the test scripts.

## Public profile and Series screening

Immediate public profile names/usernames/bios, normalized profile photos, and new or edited public Series titles/premises/published chapter text and canonical quest instructions use the fixed OpenAI Moderations endpoint with `omni-moderation-latest`. The server-only `OPENAI_API_KEY` is required; no frontend secret or general-purpose model prompt is used. Public forms ask separate explicit permission, and the Worker checks `X-Content-Review-Consent: true` before contacting the provider. Missing permission, flagged results, malformed/oversized provider responses, timeout or outage prevent the write. Rejections and outages give a friendly message without exposing provider data.

Private Series creation/save is unchanged. When an author adds or edits an unpublished future chapter in a public Series, an owner-bound service-only preflight first returns an already completed idempotent result, or validates the current version and derives the exact published quest snapshots. It compares canonical public content, chapter IDs and quest identities; unchanged public content is not resent and private text is excluded. Only selected public catalog quests or that author’s source-linked historical snapshots can be reviewed. The SQL version check still rejects any concurrent edit after this read. New or changed public metadata requires permission/screening. Public video remains a separate full operator review; this classifier is not an audio/video review or age-verification system. Moderation is fallible and report/block/operator removal remain available. No existing personal rows were sent to OpenAI during this implementation; tests use mocked responses.

Official API contract checked: https://developers.openai.com/api/docs/guides/moderation and https://developers.openai.com/api/reference/resources/moderations.
