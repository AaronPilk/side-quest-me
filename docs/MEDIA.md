# Actual media pipeline

The renderer performs real FFmpeg encoding. `node renderer/server.mjs` starts the **LOCAL DEMO** adapter on `127.0.0.1:8789`. Start Vite in demo mode in another terminal. FFmpeg, ffprobe, Node, and `npm ci` are required; Docker is not required for this adapter. Captured or uploaded files persist in `.local/media`. They never go to Supabase or Cloudflare in demo mode. Deleting the demo profile removes these media files; clearing browser storage alone does not.

`node scripts/render-fixtures.mjs` generates three eight-second synthetic fixtures, uploads all three through HTTP, renders selected seven-second segments, downloads the MP4, checks its hash, decodes all streams, and validates dimensions, duration and audio. It also exercises replacement immutability, duplicate render requests, rejected arbitrary URLs, empty/corrupt input, internal authentication, and local cross-site request protection. A fourth streaming WebM fixture deliberately has no duration header, exercising the bounded packet-timestamp fallback used for MediaRecorder output. The resulting `.local/fixtures/sidequest-proof.mp4` plays as an independent file; `sidequest-proof.jpg` comes from that actual reel. Fixture adapter data is isolated from the interactive demo. Synthetic fixtures do not replace real-device camera testing.

Measured on this workstation with FFmpeg 8.1: 21.021333-second H.264/AAC output, 1080×1920, 5,599,903 bytes, a 4.328-second render. The inputs were landscape with sound, portrait without sound, and square with sound. These are local observations, not a Cloudflare runtime or cost guarantee. The measured preset is `veryfast`, CRF 23, 30 fps, 48 kHz stereo AAC, yuv420p and MP4 fast start. The middle source gets silence; existing audio is retained unless the user mutes it.

## Capture and returning later

Each of the three story parts supports **Start recording → Stop take → Add take → Finish part**. Stop take pauses the same `MediaRecorder`; Add take resumes it. The timer and segment bar count filmed time, excluding pauses. Recording finishes at 15 seconds, and the user needs at least five seconds to finish a usable part. Camera switching is available before recording begins. This uses one continuous encoded recording per part; independent MP4 or WebM files are never joined by concatenating blobs.

Finish part opens the existing trim, framing, audio and caption review. Uploading still goes through full server validation, and the server-measured duration remains authoritative. Uploaded parts persist with the quest, so users can return later to record the remaining parts. A finished part cannot receive additional takes: restored footage can be reviewed, uploaded or replaced. The interface distinguishes this from adding takes during an active recording session.

Finished recordings and selected files also get a private local draft in IndexedDB, scoped to account, run and part. **Save draft & leave** finalizes an active recording and waits for the local save before closing. Drafts restore after refresh, expire after seven days, and are removed after a successful upload, explicit discard, sign-out, demo reset or deletion of that story's media. A draft based on a replaced uploaded clip is not restored. Drafts remain on that browser/device and are not cloud backups; storage denial or quota errors leave an explicit instruction to upload before leaving. An operating-system kill or abrupt tab closure before finalization cannot guarantee recovery.

Backgrounding or losing a camera track finalizes captured takes for review and releases camera/microphone tracks. An interrupted draft shorter than five seconds must be replaced. A late recorder callback cannot recreate drafts after sign-out cleanup. Permission denial keeps the phone-camera/file-upload options available.

Filming guidance uses the accepted quest snapshot's hook, each beat's actual action and filming direction, and its opening beat as the optional closing callback. It encourages showing the real outcome and matching the opening object, framing or movement when appropriate; it does not invent reactions or promise retention. The mobile capture screen keeps its exit control visible while recording.

Focused coverage includes a real synthetic browser recording with two paused takes, server validation of its duration, draft restoration after refresh, interruption while paused, camera/microphone release, denied-permission fallback, draft ownership/run/part isolation, expiry and sign-out invalidation. Real iOS and Android camera testing remains necessary.

## Contracts and limits

`renderer/contracts.mjs` is the shared runtime schema; `shared/media.ts` exports its types to the application. A version-1 manifest accepts a UUID run, numeric revision, UUID output generation, a plain title and exactly three ordered input IDs with start/end, mute, fit/fill, horizontal crop and story label. It rejects arbitrary URLs, file paths, commands and filter strings. Database job UUIDs identify distinct production revisions; fenced attempts are separate.

An optional `sponsorDisclosure` is at most 120 characters of plain text. In production it comes only from the immutable accepted campaign snapshot in the database manifest. The renderer visibly burns `Sponsored · [disclosure]` into the title and closing treatments, using the same escaped PNG overlay path, and holds each treatment for up to 4.5 seconds. It changes neither privacy nor awards. Existing unsponsored manifests remain valid. The fixture script creates a separate, explicitly labeled **DEMO FIXTURE ONLY · no sponsor agreement** video to verify the optional path without inventing a live sponsor.

Application limits live in `MEDIA_LIMITS`: 40 MiB per source, 5–60 seconds raw duration, 5–15 selected seconds per slot, dimensions at most 4096 per edge, three clips, 100 MiB final output, and a four-minute encoding budget. The local store is capped at 2 GiB, with at most 36 source generations per run. One renderer instance and one encoding slot prevent uncontrolled fan-out. JSON bodies are capped at 16 KiB. Probe and subprocess output sizes and execution times are bounded. Inputs with additional video/audio tracks, attachments, subtitles, unsupported containers/codecs, or decoding failures are rejected.

FFmpeg is spawned with argument arrays and no shell. All paths are generated UUID paths. Sharp rasterizes a controlled SVG containing XML-escaped text into transparent PNGs; text never enters FFmpeg filter syntax. Title/ending overlays and labels stay inside fixed conservative margins. Fit preserves the complete image on a quiet green background. Fill is an explicit choice with a horizontal framing control. FFmpeg rotates phone footage according to stream metadata before sizing and strips copied metadata from the final video.

The local HTTP API is:

- `POST /api/local-media/uploads?runId=UUID&slot=0`: raw video, slots 0–2. Returns `assetId`, generation, bytes, MIME, probe, SHA-256, `status: validated`, and preview URL.
- `POST /api/local-media/renders`: the manifest; keeps the request alive until encoding and validation finish. Returns `status: ready`, actual output/thumbnail URLs, and metadata. Repeating an identical output generation returns its original result; changing that generation is rejected.
- `GET /api/local-media/assets/UUID`, `GET /api/local-media/outputs/UUID`, and `/thumbnail` support previews; video responses support ranges. Add `?download` to download a reel.
- `DELETE /api/local-media/runs?runId=UUID` and `DELETE /api/local-media/account` remove local files. A busy upload/render returns a recoverable conflict.

Local mutations require `X-Sidequest-Demo: 1`. The listener binds loopback, rejects non-loopback Host headers and unexpected browser Origins, and does not enable cross-origin CORS. This single-developer demo is not a hosted authentication service. Only configured exact localhost origins are allowed; `LOCAL_UI_ORIGIN` can add one local development origin.

## Production transport and leases

The Worker checks the real session/account and asset ownership before granting or consuming an upload reservation. A reservation controls the run, slot, byte count, staging key and 15-minute expiry. The authenticated streaming upload route conditionally creates the staging generation once, copies the retrieved bytes to a server-only random sealed key **before** validation, then streams that sealed candidate to the container for full decoding, probing and hashing. A unique candidate transport ID avoids concurrent probe reuse. The DB transaction accepts only the latest upload generation; failed and obsolete candidates are removed. Neither a staging overwrite nor a stale reservation changes an accepted source manifest. R2 remains private.

`SidequestRenderer` extends the current `@cloudflare/containers` Container Durable Object class. It uses one stable `media-slot-0` instance, port 8789, a ten-minute idle timeout and disabled Internet access. Its internal HTTP API requires a 32-character-or-longer Worker secret. The process has no database credentials, bucket credentials or general URL fetcher. Worker-controlled streams deliver authorized input bytes; unique per-attempt transport aliases prevent a stale attempt's cleanup from removing another attempt's sources. The original immutable database manifest remains authoritative. The Worker fetches actual output bytes and stores them in R2 with a SHA-256 integrity condition before committing readiness. The container's ephemeral output is never the durable final copy.

`worker/renderer-storage.ts` wraps output and thumbnail bodies in `FixedLengthStream` before passing them to R2. Container SDK 0.3.7 forwards responses through `IdentityTransformStream`, which loses the runtime's known-length marker even when the HTTP `Content-Length` header remains. R2 requires that marker. The helper checks the declared byte count against the validated output size and cap, awaits both the source pipe and the R2 write, and aborts/cancels both on failure. It never buffers an entire reel in Worker memory; the video's SHA-256 condition remains in place. Eight real workerd/Miniflare tests reproduce the unfixed error and cover exact transfer, truncation, excess bytes, source interruption, storage rejection, checksum mismatch and a missing length.

`sq_request_render` and completion create a job and outbox intent in one SQL transaction. The Worker dispatches committed intents; the scheduled recovery pass repairs undispatched intent, stale queued jobs, and expired processing leases. Queue messages contain only the job ID. `sq_claim_render` owns the DB transition, increments a fence and sets a ten-minute lease. The consumer awaits the live container request; it does not launch a detached subprocess and return 202. `sq_finish_render` checks the active fence, lease, account and source state. A callback lost after a successful DB commit does not cause the Worker to delete the possibly committed object. Three attempts are allowed; capacity/network/interruption can retry, corrupt media and invalid selections fail. Rendering never awards XP or spends points.

The service cleans work directories on success/failure and restart, and the Worker removes per-request container assets/output after transfer. Failed validation candidates are removed. Scheduled `cleanupMedia` calls the transactional `sq_schedule_retention` function, then processes retryable deletion records. Pending uploads expire; source clips retire after 30 days only under the SQL policy that preserves pending/review/failed work and a safely retained completed reel (or an abandoned run). Final reels have no automatic expiry; the account storage quota and explicit deletion apply. Do not apply an unconditional 30-day R2 lifecycle rule to all sealed sources.

The same cleanup pass sweeps a bounded page from each staging, sealed, and render prefix, with pagination stored in a tiny private R2 operational checkpoint. An orphan must be at least 24 hours old and absent from fresh database checks of source/output/staging/thumbnail references before deletion. A database lookup failure prevents candidate deletion. The grace period exceeds both upload authorizations and fenced job leases, so an abandoned candidate cannot become a valid late commit. Never blindly delete an output after an ambiguous commit.

## Production deployment and remaining verification

The first full production deployment completed on 2026-09-30 through [GitHub Actions run 36740095380](https://github.com/AaronPilk/side-quest-me/actions/runs/36740095380). It installed the `sidequest-me` Worker, queue consumer and `sidequest-me-sidequestrenderer` Container. The GitHub runner built the pinned official Node 22 Bookworm image with Debian FFmpeg 5.1.9 and DejaVu fonts. The image uses the repository's single lockfile, runs as the unprivileged `node` user and exposes only the internal service. Docker remains unnecessary for local demo development.

The first production smoke verified three authenticated synthetic uploads and validation. Cloudflare traces showed that the 15-second reel encoded successfully in about 146 seconds, but its subsequent R2 transfer failed immediately because the stream had no runtime-known length. No durable ready reel was claimed. The fixed-length transfer patch passed the local workerd regression above and deployed with commit `5eb1dac` in [GitHub Actions run 36745483095](https://github.com/AaronPilk/side-quest-me/actions/runs/36745483095).

That release configured **1 vCPU, 3 GiB RAM, 4 GB disk**. Its production smoke passed authenticated profile persistence, 1,113-candidate catalog checks, exact-plan pagination, ownership isolation and three validated 16-second synthetic source uploads. However, rendering three 15-second selections failed after about 250 seconds from job claim, with the old `invalid_media` classification and no promoted output. This timing is consistent with the renderer's 240-second encoding budget plus source transfer, but the underlying command exception was not captured by the sampled logs. Both temporary accounts and their media were fully removed by 16:45:26 UTC. This was a failed maximum-duration verification, not a ready reel.

The repository now selects a custom **2 vCPU, 6 GiB RAM, 4 GB disk** Container, keeping `max_instances: 1` and queue `max_concurrency: 1`. The original `basic` instance supplied only 0.25 vCPU, and the configured 1-vCPU release did not pass the maximum-duration fixture. Cloudflare requires at least 3 GiB per custom vCPU. Encoding remains 1080×1920, 30 fps, `veryfast`, CRF 23. The new resource choice and a fresh image must pass a complete 45-second production render before maximum-duration support is considered verified; that rollout and verification remain pending here.

For subsequent releases, build using the repository root as Docker context and the selected environment configuration. Confirm the Worker, Container rollout, queue consumer and private R2 transfer together. Production verification must download and probe the finished H.264/AAC reel, check its byte count/hash and all three parts, exercise account isolation, and finish deletion of temporary verification media/accounts. Continue separate tests of stale reservations, queue duplication, crash/retry, output fencing and expired capabilities. Measure realistic phone clips before raising limits or promising runtime/cost.
